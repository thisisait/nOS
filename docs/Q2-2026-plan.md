   These are opposite policies and `w-release` does not pick one.
   `docs/archive/release-readiness-v010.md` measured v0.10 at three to four weeks

5. **`w-datalog`: is there a consumer?** No agent skill, Wing view or KEAP endpoint

6. **Commit signing: turn it on, or drop `required_signatures` from ruleset

## 4. On the minimax question, directly

The operator asked that minimax be able to drive the whole suite — the loop,
Hermes, and the master session. The chapters answer it in three parts.

**The agents: yes, but not measurably yet.** `backend: minimax` is declared on
librarian and surveyor, `NOS_ARMED_BACKENDS=minimax` is live in the running
wing.plist, and the provider console shows usage. The ledger records
`model_uri = cli:unrecorded` and has **zero** sessions naming minimax, because
`pulse-run-agent.sh` never evaluates `BindingResolver` at all — it just sets env
vars. So the compliance gates that `state/llm-backends.yml` documents (Article-30
processor match, opus-refusal, no-degrade) **have never fired on a run that
happened.** Item 11 is what makes the binding both real and legible; expect a
first cutover to *start refusing* runs that silently succeeded, which is correct
behaviour and will read as a regression unless announced.

**Hermes: no, and it is a different mechanism.** `cli-config.yaml.j2` hardcodes
an OpenAI-compatible provider pointed at local Ollama, with no reference to
`llm-backends.yml` or `BindingResolver`. MiniMax is registered as an
**anthropic-protocol** endpoint. Wiring it needs either MiniMax's OpenAI-compat
surface or a shim, plus re-implementing the compliance gates for Hermes
specifically. Unbuilt, separately sized, not a consequence of item 11.

**The master session: excluded by a standing written decision, not a gap.**
`docs/minimax-groundwork.md` states the requirement as every cloud agent *except*
the operator's own interactive thread. Mechanically reversing it is a one-line env
export; it is an operator call, not engineering.

### 5.1 `w-agentkit-spine` — needs-a-decision-first

Two runtimes: `pulse-run-agent.sh` → bare `claude --print` runs all nine nightly
ceremonies; AgentKit's `Runner.php` records real sessions, iterations, grader
verdicts and lineage but drives exactly one live ceremony (`migration-author`).
The wiring is far more built than the row admits — `ClaudeCliAdapter`,
`AnthropicAdapter`, `BindingResolver` and `tools/run-agent.sh` all ship and are
gate-tested. Missing: eight `command:` lines and one open question.

**MVP** — (1) cut over the six CLI-only agents (conductor, curator, scout,
remediator, upgrade-advisor, upgrade-architect); none declares a `backend:`, so
none touches the unproven bound loop. Proof: a pytest per agent shaped like
`test_migration_author_agentkit.py`, plus a live run showing a real `model_uri`.
(2) **Close the mutex gap first** — `agent-run-lock.sh` serialises the shell
bridge and `loop-propose.py`; `Runner.php` and `ProcessPool.php` contain zero
reference to it. (3) Never invoke `bin/run-agent.php` bare from a catalog entry —
a bare invocation appended **37 unsigned rows** to the hash-chained `events` table
on 2026-08-16/18; always `tools/run-agent.sh`, and check both allow-lists.
(4) Hold librarian and surveyor out as a decision, not a rollout step.

**Hidden fees** — `runner_status` labels disagree with the measurement (librarian
reads `on-demand`, surveyor `unproven`, while the evidence names both showing the
identical failure) · the mutex does not know AgentKit exists · **the cutover is a
compliance-enforcement change wearing a runtime-swap costume**, so a job that
silently succeeded may start refusing.

**Cost** ~1–1.5 d for steps 1–3. Step 4 is calendar time, not work-hours.

### 5.2 `w-datalog` — needs-a-decision-first

**Read `docs/idea/02-cortex-lang.md:165-205` as the spec, not the roadmap row.**
The row's body is the original, since-disproven framing; the design doc has
absorbed a full adversarial correction the row never picked up. An implementer
working from the row will re-derive three already-fixed defects.

**MVP** — vendor with three declared divergences, not byte-identical: strip two
semantica-internal imports; add `max_derived_facts`/`max_iterations`/`max_seconds`
failing closed; rewrite the parser to raise on unconsumed input (upstream's regex
`findall` silently drops `not` and comparison guards, inverting rule semantics).
Gate the read surface to `tax:`/`rel:` at the same layer `NAMESPACE_POLICY`
enforces. Ship as a bounded seeded query, not derive-everything. Land results as
`source='derived', status='proposed'` through the existing moderation queue.

**Hidden fees** — the budget numbers were measured on a synthetic **chain**
(312,444 facts / ~142 s over 790 nodes); the live graph branches, and nobody has
run the fixture against it, so the defaults are a guess about the real blast
radius · `test_a_vendored_copy_honors_the_declared_conditions` is currently
**vacuous** — it rglobs for a file that does not exist and reports green, the
same `0/0 ready` shape · the row's own body is a fee, since a future probe author
could encode its falsehood as ground truth.

**Cost** 2–3 d. Estate pays a second execution model beside the pipeline IR, and
a vendored third-party file that — unlike the KEAP port — **nothing watches for
upstream drift**; `cortex-drift.py` does not cover it.

**Order finding** `w-exec-pipe` sharpens rather than shrinks the case: even a
working flat pipeline has no recursion, `branch` is excluded by design, and the
16-stage cap makes unrolling an unbounded ancestor walk structurally impossible.
And `kpro-ids` does **not** gate this row — Datalog's `tax:`/`rel:` scope never
touches the physical `fs:` ids.

### 5.3 `loop-forget` — needs-a-decision-first

**The row's premise is false as written.** The mechanism exists, is written and is
read — under a different name than the probe greps for. `loop_attempts` was never
the design; `loop_proposals.fingerprint` + `attempt_n` + `DEFAULT_MAX_ATTEMPTS`
is, declared in `ledger.py`'s own `_DDL` and applied straight to `wing.db`,
bypassing the PHP schema file the probe reads.

**MVP** — (1) correct the row and the probe; (2) confirm every CI/reporting gate
reads a temp DB, not the live one (~1 h audit); (3) **operator decision**: chain
re-genesis for the nine fixture rows, cheap today at three days old, "impossible
in practice in a year" — `loop_verdicts` is WORM-triggered so they cannot simply
be deleted.

**Explicitly not built:** a new `loop_attempts` table — a second competing memory
beside a working one.

**Hidden fees** — a queue-wide `committed` flag gates an entire source's
`evidence_committed`, so one dirty unrelated line withholds *every* `rem:`
weakness until committed · the probe greps the PHP schema file on principle, so
any future "does the loop have table X" probe written that way gets a false
negative for everything the loop actually owns.

**Order finding** `loop_proposals` is structurally a **loop** table, not an
AgentKit one — Dreams is narrative continuity; the ledger needs forgery-resistant
WORM shape Dreams was never built for. The real link is that `proposer_id` is a
bare string today; when the spine lands, *that* is when it becomes a reference to
`agent_sessions.uuid`. And `loop-queue-retires` is a **different** forgetting,
proven by the same row: REM-204 shows the loop correctly refusing to re-propose
while the queue never learned it succeeded.

### 5.4 `w-fixture` — ship-as-MVP

Nine EN 16931-shaped tables, a deterministic seed, an idempotent converge seeder
and an offline referee are **already committed** (`8165de48`, `debdc6ca`,
`fc8fc522`). What has not happened is a live converge:
`keap_seed_business_fixture` defaults false.

**MVP** — flip it in `config.yml` and converge KEAP · run the design doc's
**proof 3** (`nos --remove=data --confirm` → reconverge → identical slugs and
counts; the doc calls this "the one most likely to fail") · run **proof 1**, ask
"which jobs miss their deadline if the finisher stops" through a validated cortex
chain and match a hand-computed answer · record a decision on the orphan
`Business partners` table · **stop there — no real customers.**

**Hidden fees** — **the GDPR gate the row claims this exercises does not fire**:
the seeder POSTs straight to `/agent/v1/tables`, never through
`nos_app_parser`, so the only thing stopping real customer data is a pytest regex
over one seed file; KEAP's write path has no synthetic-data check at all ·
`changed_when` is permanently true, so nine tasks report changed at steady state
and will mask real drift · tier-2 managers can read and delete fixture rows but
**cannot update one**, because the human door 404s PATCH/PUT.

**Corrections to the brief** — `rowRef` **already shipped** (2026-08-09, verified
against `~/keap/src`); it has simply never carried a live write, which is what
proof 1 provides. And `backup-drill-keap-db` does **not** block the synthetic
increment, because the fixture's recovery path is reconverge-from-git, not
restore-from-backup — it becomes load-bearing the moment real people enter,
exactly parallel to the Article-30 rule.

### 5.5 `w-release` — needs-a-decision-first

The checklist itself is shippable; the **binding** cadence is not, yet.

## 6. What this plan is not

It is not a commitment to dates. Every cost above is an estimate made by an agent
that read the code but has not written it, and the estate's own record —
`release-readiness-v010.md` — is that the gap between those two numbers has been
3–4× at least once.

It is also not complete. Four tracks (`face`, `filesystem`, `platform` beyond
items 0 and 6, and the remainder of `agents`) were not given a chapter. Their rows
are still in the table and still unread by this pass, and a plan that did not say
so would be making the same claim `0/0 ready` makes.
