## 1. Problem / why

The "Devlog platform + docs consolidation" epic landed across three phases (A docs-consolidation,
B platform/pipeline, C release-ceremony + GH-Pages). `docs/active-work.md` already lists all three
as effectively done and the machinery is real and gated:

- **Compiler + bundle** — `tools/devlog-compile.py` → byte-deterministic `state/devlog-bundle.jsonl`
  (17 entries today), pinned by `tests/anatomy/test_devlog_bundle.py`.
- **Sync engine** — `files/anatomy/scripts/devlog-sync.py` driven by `tasks/devlog-sync.yml`
  (`--tags devlog`), contract-pinned by `test_devlog_sync_contract.py` + `test_devlog_event_types.py`
  + `test_devlog_wp_provisioning.py`.
- **Renderer** — `tools/devlog-render.py` (GH-Pages), pinned by `test_devlog_render.py`.
- **Skill** — `.claude/skills/devlog/SKILL.md`, pinned by `test_devlog_skill_contract.py`.
- **Release ceremony** — `tools/devlog-release.sh`.

So the epic is **not** an open build. What is genuinely open, and what this v0.7 item delivers, is
the **consolidation-and-pin pass that an epic of this size needs before a release tag carries it**:

1. **No single committed record ties the three phases together.** The narrative lives only in
   `~/.claude/plans/federated-hugging-snowflake.md` (a local, uncommitted plan) and in scattered
   `active-work.md` bullets. A future archaeologist has no committed "what shipped, in which phase,
   pinned by which gate" map. The epic deserves one **nos-core devlog entry** (the platform is
   literally built to hold exactly this kind of record — eating our own dog food) plus a one-line
   `RELEASE.md` v0.7 pointer.
2. **The phase boundaries are not test-pinned as a set.** Each piece has a gate, but nothing asserts
   the *epic-level invariants* an agent could silently regress: (a) every committed nos-core entry's
   `related:` repo paths actually exist; (b) the WordPress-write audit rule ("never raw curl,
   helper-only") holds across the whole toolchain, not just the skill doc; (c) a `release-vX.Y`
   entry exists for every shipped tag the bundle claims via `release:` frontmatter. These are the
   "the epic stays coherent" properties, currently unguarded.
3. **`active-work.md` is at its 150-line ceiling** (pinned by `test_active_work_slim.py`) and still
   carries the epic as "Now". Per pointer-doctrine the completed epic narrative must move to the
   devlog, freeing the `active-work.md` "Now" slot for the real current track. Doing that move
   *without* first writing the devlog entry would lose the narrative — hence the ordering below.

This item is therefore a **documentation + gate-hardening pass**, not new platform code. It converts
an implicitly-finished epic into an explicitly-recorded, test-pinned, release-ready one — matching how
every prior epic closed (devlog entry + `RELEASE.md` pointer + a gate that stops regression).

## 3. Approach (step order)

1. **Write the devlog entry first.** Author `2026-06-14-devlog-epic-abc.md` with valid frontmatter and
   the A/B/C body. Use `/devlog new` if scaffolding helps, but a hand-written file matching the README
   schema is fine. Set `related:` to real repo paths only (the new gate will enforce that).
2. **Recompile the bundle.** `tools/devlog-compile.py` (no `--check`) to rewrite
   `state/devlog-bundle.jsonl`. Confirm the new entry lands and the bundle is byte-deterministic
   (`--check` returns clean afterward).
3. **Write the epic-coherence gate (§4).** Run it green against the recompiled tree. The `related:`
   existence check and the `release:`-has-an-entry check both depend on step 1 being correct — if
   they go red, fix the *entry*, not the gate.
4. **Move the pointers.** Add the `RELEASE.md` v0.7 line; slim the `active-work.md` "Now" block;
   archive/distill the local plan reference. Re-run `test_active_work_slim.py`.
5. **Run the full devlog gate cluster + anatomy suite + `--syntax-check` (§6).** Iterate to green.
6. **Commit** to `feat/v0.7-overnight` (Conventional Commit, surgeon tone). No push.

The change is **docs + a new gate + a regenerated committed bundle** — zero live mutation, zero
playbook-behaviour change. The devlog only reaches WordPress on the next operator `--tags devlog`
run, per machinery doctrine; this commit just stages the content + bundle.

## 4. Gates it needs (`tests/anatomy/test_devlog_epic_coherence.py`)

All offline, fast, pure file-scan + in-process compiler import — no Docker, no network, no live
WordPress. Pattern mirrors `test_devlog_bundle.py` (compiler imported via `importlib`).

**`test_entry_related_paths_exist()`**
- For every nos-core entry, every `related:` value that looks like a repo path (no `://`) must resolve
  to a real file/dir under `REPO`. Pins the "narrative links don't rot" property across the whole
  devlog, the failure mode the epic entry is most exposed to (it lists ~8 tool/test paths).

**`test_release_tag_has_release_entry()`**
- For every distinct non-empty `release:` value in the bundle, assert a devlog entry exists whose `id`
  or `tags`/`title` marks it as that release's narrative (the `release-vX.Y` convention — see the
  existing `2026-06-12-release-v0-6-beta.md`). Pins "a tag the bundle claims is actually narrated."
  Scope to the convention already in the tree; if a `release:` value legitimately has no standalone
  entry yet, allowlist it with a one-line reason (image-pin-hygiene precedent) rather than weakening
  the assertion.

**`test_devlog_writes_are_helper_only()`**
- Grep the devlog toolchain (`tools/devlog-*.py`, `files/anatomy/scripts/devlog-sync.py`,
  `tasks/devlog-sync.yml`) for a raw WordPress-write smell: a `requests.post`/`curl` to a `wp-json`
  URL that is NOT inside `devlog-post.py` / `devlog-sync.py` (the two sanctioned writers). Promotes the
  skill-doc-only audit rule (`test_devlog_skill_contract` only checks the SKILL.md *text*) to a
  toolchain-wide invariant — the actual "never raw curl" doctrine, pinned in code.

**Also keep green (existing devlog cluster, must not regress):**
`test_devlog_bundle.py`, `test_devlog_render.py`, `test_devlog_sync_contract.py`,
`test_devlog_event_types.py`, `test_devlog_wp_provisioning.py`, `test_devlog_skill_contract.py`,
`test_active_work_slim.py`.

## 5. Risks

1. **Bundle determinism / markdown pin.** `state/devlog-bundle.jsonl` is byte-deterministic and pinned
   to `MARKDOWN_PIN = "3.10.2"` in `tools/devlog-compile.py`. If the dev box has a different
   python-markdown, the recompile bytes differ and `test_devlog_bundle.py` flaps (it `skip`s on a pin
   mismatch). **Mitigation:** confirm `python -c "import markdown; print(markdown.__version__)"` ==
   3.10.2 before committing the regenerated bundle; if it differs, recompile under the pinned version
   (the CI pytest job installs the pin) and never hand-edit the JSONL.
2. **`related:` path drift in the gate itself.** The new `test_entry_related_paths_exist` is only as
   honest as the entry's `related:` list — a wrong path turns the gate red. **Mitigation:** point
   `related:` exclusively at paths verified to exist at author time; the gate then *keeps* them
   honest going forward (its whole purpose).
3. **`active-work.md` 150-line ceiling.** Slimming the "Now" block must not push the file over the
   ceiling pinned by `test_active_work_slim.py`. **Mitigation:** the move is net-negative lines
   (replace a multi-line block with a one-line pointer or delete it); re-run the gate.
4. **`release: v0.7-beta` claimed before the tag exists.** Setting `release: v0.7-beta` on the entry
   asserts a tag that isn't cut yet. The new `test_release_tag_has_release_entry` checks the *inverse*
   (every release value HAS a narrative entry), so this is self-consistent — but if a separate gate or
   the release ceremony asserts the tag exists, set `release:` only once v0.7 is actually being cut,
   or use `status: draft` (excluded from the bundle) until then. **Mitigation:** the safest author
   choice is to ship the entry now with no `release:` (or `release: v0.7-beta` since this *is* the
   v0.7 content), and let `tools/devlog-release.sh` reconcile at tag time — confirm against the
   ceremony script's expectations during implementation.
5. **Stock-Jinja vars trap — N/A here.** This item adds no var to `default.config.yml` /
   `default.credentials.yml`, so `test_config_stock_jinja_only.py` is untouched. Flagged only to
   confirm it was considered.
6. **Over-claiming "epic complete".** The devlog entry must describe what *shipped*, not aspirational
   pieces. Cross-check each phase claim against a real file + gate before writing it (the §1 inventory
   is the source). Do not narrate the deferred follow-ups (Infisical MTI, tofu adopt-path, etc.) as
   part of this epic — they are separate `active-work.md` items.
