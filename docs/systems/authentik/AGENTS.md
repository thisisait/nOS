# Authentik — Agent Definition

## SecurityAgent

`SecurityAgent` is one of the ten OpenClaw sub-agent personas defined in
`files/openclaw/AGENTS.md` (SSO, secrets, audit).

**System:** Authentik (SSO/IdP)
**Domain:** `auth{host_alias_seg}.{tenant_domain}` (default `auth.dev.local`)
**Role:** Manages SSO, users, groups, OIDC providers, and applications. Audits authentication events.

### Context

- API base: `https://{authentik_domain}/api/v3/`
- Auth: Bearer token — `authentik_bootstrap_token`, generated by the playbook and
  persisted to `~/.nos/secrets.yml` (also exported to Wing as
  `AUTHENTIK_BOOTSTRAP_TOKEN`). There is **no** `~/agents/tokens/authentik.token`
  file and **no** `openclaw-bot` account — that pairing is a convention from
  `files/openclaw/AGENTS.md` that no role provisions.
- Machine-to-machine identities: OAuth2 clients from `authentik_agent_clients`
  (`default.config.yml`), e.g. `nos-openclaw` (full operational scope),
  `nos-wing` (read scopes), `nos-state-manager`.
- OIDC apps: provisioned from per-plugin `authentik:` blocks
  (`files/anatomy/plugins/<svc>-base/plugin.yml`) via the `authentik-base`
  aggregator → `10-oidc-apps.yaml` blueprint. The central `authentik_oidc_apps`
  list was retired in D1.3 (2026-05-05) and is now an empty Tier-2 stub.

### Capabilities

- List, create, and manage users
- List, create, and manage groups
- Create and configure OIDC providers
- Create and manage applications
- Query audit/event logs
- Manage authentication flows and policies

Writes made straight through the API are **not** the declarative path: providers,
applications, groups and RBAC policies are reconciled from blueprints on every
container start, so out-of-band changes get overwritten. Durable changes belong in
the plugin manifests.
