# OpenHuman — the desktop agent, set up by one command (roadmap `openhuman`)

Set `install_openhuman: true` in `config.yml`, then run `ansible-playbook main.yml --tags openhuman`.

## What the role does, in order (`roles/pazny.openhuman`)
1. **Installs the app as a symbiont.** Cask `openhuman` from `homebrew_symbiont_casks`. It is installed only when neither `Caskroom/openhuman` nor `/Applications/OpenHuman.app` exists, and nOS never upgrades or removes it: the cask is `auto_updates`. The run reports which copy it found.
2. **Stops if the app is running.** OpenHuman rewrites `config.toml` whenever it saves, so with the app open the role writes nothing and tells you to quit it and run again. `--tags verify` still reports what is on disk.
3. **Makes the local session with the app's own CLI** — what "Set it up myself" does, without the GUI. The bundle's binary runs core methods in-process: `OpenHuman.app/Contents/MacOS/OpenHuman core call --method <method> --params <json>` ([cli.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/core/cli.rs)). The role calls `openhuman.auth_set_credential` with the same unsigned local token the app builds ([localSession.ts](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/app/src/utils/localSession.ts)). It does this only when `~/.openhuman/active_user.toml` names nobody, so an existing local or cloud login is never replaced.
   *Where the token goes:* not the macOS Keychain. The release cask runs with `OPENHUMAN_APP_ENV` unset, so the app and the CLI both use the plain file backend: `~/.openhuman/dev-keychain.json`, mode 0600 ([store.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/security/keyring/store.rs) `build_backend_at`). The token is the unsigned local one (`alg: none`, no backend account behind it), so the risk is low; it is written down here so nobody looks for it in the Keychain.
4. **Writes `config.toml` in every profile.** It merges the declared keys (privacy mode, analytics and usage sharing off, core updater off, remote gitbooks MCP off, `[cron] enabled = false`, `memory.engine` (v0.64.15 has no local memory store and the default engine `tinyhumans` is their cloud, so with KEAP it is `cortexdb` at KEAP's hippocampus, `http://127.0.0.1:<keap_port>/hippocampus`, conversations and recall on; without KEAP, `none`), the model route, the background routes — summaries, embeddings, learning — on Ollama with `nomic-embed-text` at 768 dimensions, Ollama on `127.0.0.1:11434`, the nOS tables MCP server) into whatever is already there. Keys it does not declare are kept, but comments are not. It declares schema keys only: the app's save drops any other key.
   *Profiles.* OpenHuman keeps one directory per user under `~/.openhuman/users/`. Before any login it uses `users/local`. The local session uses `users/local-<host>`, where `<host>` is the hostname lowercased with every run of other characters turned into one `-` (`Studio.local` → `local-studio-local`; [session_support.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/security/credentials/session_support.rs)). A cloud login uses `users/<account id>`. `active_user.toml` names the one in use. The role writes every profile on disk plus `users/local` and the predicted `users/local-<host>`, so nothing needs a second run after the first launch. Only a later cloud login or a hostname change makes a profile the role did not see: run `--tags openhuman` again. `--tags verify` fails while any profile is off the declared route.
5. **Stores the wizard's tool choice.** The wizard's last step saves a tool list (`onboardingTasks.enabledTools` in `<profile>/workspace/state/app-state.json`); with none stored, OpenHuman turns on every tool, including ~160 opt-in ones a wizard user has off ([user_filter.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/tools/user_filter.rs)). The role stores the wizard's own default, `openhuman_enabled_tools` in the role defaults (every `defaultEnabled` entry of [toolDefinitions.ts](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/app/src/utils/toolDefinitions.ts)), with `openhuman.app_state_update_local_state`. It runs only while no list is stored, so a choice made later in Settings → Tools is kept.
6. **Cron is off.** OpenHuman turns cron on by default, and step 7 seeds proactive jobs (a morning briefing). A reference twin to test against must not act unasked, so `[cron] enabled = false`.
7. **Marks onboarding done** with `openhuman.config_set_onboarding_completed {"value": true}`, because the local login resets it. The method (not the bare flag) also seeds OpenHuman's proactive cron jobs ([ui.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/config/ops/ui.rs)). It runs only while the flag is not already true.
   *A re-login undoes it.* Logging in locally again inside the app sets `onboarding_completed = false` (upstream, [credential.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/security/credentials/ops/credential.rs), the `CredentialKind::Local` branch), so the wizard shows on the next launch. nOS cannot stop that. `tools/openhuman-status.py` shows it as `onboarding` RED; the fix is to quit the app and run `--tags openhuman`, which sets it back.
8. **`workspace/AGENTS.md`** in each profile is a copy of `IMPRINT.md` with one provenance line. It is rewritten on every converge, so edit `IMPRINT.md`, not this copy. OpenHuman reads at most 20,000 characters of it (`BOOTSTRAP_MAX_CHARS`, [types.rs](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/crates/openhuman-core/src/agent/prompts/types.rs)) and cuts the rest; the reader's `imprint` line is RED when the copy is longer or no longer matches.
9. **Memory in KEAP.** KEAP v2.1.0 serves the CortexDB wire under `/hippocampus`; every memory is a row of the `engram` DataTable, owned by `agent:openhuman`. The key is derived (`keap_hippocampus_openhuman`), reaches KEAP as `KEAP_HIPPOCAMPUS_KEYS`, and reaches OpenHuman only through `openhuman.memory_engine_set`, which stores it in the keychain file, never in `config.toml`. It opens `/hippocampus` and nothing else. KEAP's post-start verify asks the route for health without a key and expects 401; this role's verify skips that line, because the role runs before stack-up rebuilds KEAP.
10. **Skills** (`openhuman_skills`, default `nos-datatables`) are copied into `~/.openhuman/skills/`. They are not linked, because OpenHuman rejects symlinks.
11. **MCP: the nOS tables, read-only**, as a `[[mcp_client.servers]]` entry named `nos-tables` in `config.toml`. That table is the static server set the core reads at boot (`mcp::host::static_registry`); a server you added yourself, by name, is kept. `env` takes literal values only, so `/bin/sh -c` reads the RO token from `iiab-keap-1` each time the server spawns, and it is never stored. The repo path is `nos_main_checkout`. (The `mcp.json` tab in the app edits a second, dynamic store, `mcp_clients.db`. nOS does not touch it.)
12. **The Little Snitch rule group** `~/.openhuman/nos-openhuman.lsrules` denies OpenHuman every remote host. Little Snitch does not filter loopback.
13. **Verifies.** It runs `tools/openhuman-status.py` (tag `verify`): one line per profile (cron included), the twin lines for the active profile (`session`, `onboarding`, `tools`, `imprint`), plus a check for a second Ollama (another binary, or a port other than 11434). Any RED fails the play. UNKNOWN does not fail it: an idle app or the desktop updater can only show UNKNOWN.

## What nOS cannot do: three things by hand
- **Gatekeeper, on a fresh host.** The first launch of a freshly installed cask shows the macOS "downloaded from the internet" dialog; click Open once. nOS installs the cask with brew's default quarantine; dropping it (`--no-quarantine`) is the operator's call, not the role's.
- **The walkthrough tour, once.** After onboarding the app starts a short tour of its screens. Its "done" flag lives in the app window's localStorage (`openhuman:walkthrough_completed`, [AppWalkthrough.tsx](https://github.com/tinyhumansai/openhuman/blob/v0.64.10/app/src/components/walkthrough/AppWalkthrough.tsx)); no CLI or core method reaches it, so skip or finish it once.
- **Firewall: import `nos-openhuman.lsrules` in Little Snitch.** The `littlesnitch` CLI has no rule-import command. Its `restore-model` replaces the whole configuration, which is too destructive to use for this. LuLu has no rules-file CLI, so with LuLu you add the same rule by hand. pf cannot filter per app, so nOS ships no pf rule.

## Provider: local model or your Claude subscription
| `openhuman_provider` | route | privacy | leaves the Mac |
|---|---|---|---|
| `ollama` (default) | `ollama:<ollama_small_model>` (`hermes3:8b`) | `local_only` | nothing |
| `claude-code` | `claude-code:<model>` (`openhuman_model`, default `sonnet`) | `standard` (`local_only` refuses every CLI delegate) | prompts, via the `claude` CLI |

The claude-code mode drives the `claude` binary that `tasks/claude-cli.yml` manages. It must be version 2.0 or newer and logged in (`claude login`; on macOS the credential lives in the Keychain). Leave `ANTHROPIC_API_KEY` unset so the subscription is used ([provider guide](https://github.com/tinyhumansai/openhuman/blob/main/gitbooks/developing/providers/claude-code.md)). The connections come from the `claude` process, not from OpenHuman, so the OpenHuman rule stays deny-all. The `claude` rule must allow `api.anthropic.com` (inference), `platform.claude.com` (OAuth refresh) and `claude.ai` (sign-in) ([network requirements](https://code.claude.com/docs/en/network-config)). In this mode Anthropic (US) becomes an Art-30 processor (see `openhuman-base/plugin.yml`).

## 10-minute acceptance: ask, then check with the reader
| # | Ask OpenHuman | Check with | It works when |
|---|---|---|---|
| 1 | "How many roadmap rows are `next`?" | `nos dtt status` | the same count, from `nos_tables read-rows` |
| 2 | "What does roadmap row `openhuman` say, and what is its status?" | `nos dtt status \| grep openhuman` | same title and status, quoted from `get-row` |
| 3 | "Which roadmap rows are `doing` right now?" | `nos dtt status` | same set, no invented rows |
| 4 | "Run `tools/red-status.py` and give me the first red line." (approve the shell call) | run it yourself | identical first red line |
| 5 | "Set roadmap row `openhuman` to `doing`." | `nos dtt status` unchanged | it reports 401/403 (reader tier) and does not retry |

A pass needs all five: answers 1–4 match the readers, question 5 is refused, and `tools/openhuman-status.py` shows `egress` OK during question 4. The Little Snitch log should show **denied** attempts (`api.tinyhumans.ai`, `github.com` updater, Sentry), not silence.

## What this is, and is not
- It belongs to the "runs as the user" attacker class (`ssot/doctrine/session-threat-model.md`). Only three things contain it: the firewall rule, the RO token and your approvals.
- The headless core (`apps/openhuman.yml.draft`) is a later step. Promoting it must give it its own toggle.
- Not yet verified on a real launch: the CLI session path end to end on a fresh host, the stored tool list taking effect, whether the static `nos-tables` server shows up in the app, and the Little Snitch rule's process path (`OpenHuman.app/Contents/MacOS/OpenHuman`).
