# C1 gap: the organ's tree is missing the self-model (91 nodes)

Found 2026-07-25 by comparing the materialised organ store against the live KEAP
container, after P-4 steps 1–8 landed green.

## The measurement

| store | `taxonomy_nodes_ext` | `node_descriptions` |
| --- | --- | --- |
| organ (`~/cortex/data/keap.db`, materialised from git) | 960 | 1750 |
| live KEAP (`iiab-keap-1:/data/keap.db`) | 1051 | 1841 |

Difference: **exactly 91 in both**, and every one of the 91 ids the organ lacks
sits under the `nos` root — `nos`, `nos.b2b`, `nos.b2b.erpnext`,
`nos.b2b.erpnext.credential`, … i.e. **the whole nOS self-model tree**.

Both repos' `knowledge/canonical/` hold the same 107 files, so this is not a
checkout skew. The self-model is generated by `roles/pazny.keap` at converge time
and written into the container's mounted canonical directory; it is not a
git-committed artifact of the KEAP repo, so an organ that materialises "from git"
cannot see it.

## Why it matters, concretely

The self-model is not an edge case for this organ — it is most of what anyone
will validate against:

- Every operand in nOS's 261-case recall set is a `nos.*` node. Against the organ
  as it stands, all 261 resolve to `unknown_operand`.
- Wing's executor validating `tax:nos.b2b.erpnext` gets a refusal today. The
  refusal is *correct behaviour on a tree that lacks the node* — which is exactly
  why it is dangerous: it looks like a well-formed answer, not like a missing
  corpus.
- The organ and live KEAP therefore compose different trees, so their
  `onto1:` digests differ. Under C1 that is tolerable only because KEAP is not
  the validation authority; it becomes a correctness problem the moment both
  answer.

This does not contradict the C1-needs-no-migration finding. The claim was that
`validate` reads nothing but the composed tree, the verb registry and the store's
own identity — that still holds, and `knowledge_objects` is still correctly empty.
What was wrong was the unstated assumption that **"the tree" and "KEAP's git"
are the same set.** They are not: the tree is git *plus* whatever the converge
generates.

## What closes it

The generator is nOS's, so this is nOS-side wiring, not a KEAP change. Three
options, in the order I would weigh them:

1. **Run the self-model generator into the organ's store at materialisation
   time** — the organ already shells out to `knowledge/ingest.mjs`; the generator
   is the same shape of step. Keeps one source (the generator) and no new copy.
2. **Have the generator write its canonical output to a path both consume.** One
   artifact, two readers. Cheaper than (1) but introduces a shared directory
   whose ownership needs stating.
3. **Commit the generated self-model into a git tree the organ reads.** Most
   reproducible, but it makes generated output a reviewed artifact and it will
   drift from the estate between converges — the thing the generator exists to
   prevent.

Whichever is chosen, the organ should **assert its own coverage** rather than
discover this again by comparison: a materialisation that produces no `nos.*`
root when one is expected should fail loudly, in the same spirit as the recall
gate's exit 4 — a tree that silently lacks the domain everything references is
the "corpus exhausted" class of lie.

## What is NOT wrong

- Port fidelity holds: 14 of 15 ported modules are byte-identical to KEAP
  v1.27.0, and the 15th (`server/migrations.ts`) differs only by a comment block
  added on the KEAP side *after* the port snapshot (KEAP `273de0e`, the
  dead-schema note). No behavioural divergence, no effect on `onto1`.
- The hard gate is genuinely green: with the input state the digest is defined
  for — 790 spine nodes, zero ext rows, 16 seed verbs — the organ reproduces
  `onto1:76d1f3ad728b382b`.
- The materialised store reporting `onto1:6f9c20ae8c8464af` is **not** a
  mismatch. That is a different input state (790 + 960 ext), and a different
  state legitimately yields a different digest.
